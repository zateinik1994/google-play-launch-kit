# Метаданные Google Play

Проверено: **2026-10-14**. Это снимок правил; перед отправкой сверять указанные официальные страницы и ограничения конкретного приложения в Play Console.

## Поля листинга

| Поле | Предел | Назначение |
| --- | ---: | --- |
| App name / `title` | 30 символов | Название и понятный основной сценарий |
| `shortDescription` | 80 символов | Краткая ценность приложения |
| `fullDescription` | 4000 символов | Возможности, условия использования, ограничения |

Лимиты одинаковы для полноширинных и обычных символов. Повторение нерелевантных ключей может нарушать политику. Источник: [Create and set up your app](https://support.google.com/googleplay/android-developer/answer/9859152?hl=en-GB).

У Google Play Listing API есть `language`, `title`, `shortDescription`, `fullDescription`, `video`; отдельного скрытого поля keywords и поля subtitle в этой схеме нет. Apple keyword bank нельзя загрузить как метаданные Play. Источник: [Listing resource](https://developers.google.com/android-publisher/api-ref/rest/v3/edits.listings).

## Локали

API описывает `language` как BCP-47, но корректный синтаксис тега сам по себе не подтверждает поддержку листингом. Проверять код по [списку доступных языков Play Console](https://support.google.com/googleplay/android-developer/answer/9844778?hl=en) и доступным переводам приложения. Примеры из списка: `en-US`, `en-GB`, `ru-RU`, `tr-TR`, `kk`, `uk`, `id`, `iw-IL`, `es-419`, `pt-BR`. Не превращать автоматически `ru` в `ru-RU`, `he` в `iw-IL` или `de-AT` в `de-DE`: явно выбрать поддерживаемую локаль и проверить ее в Console. Страна распространения, язык листинга и язык интерфейса приложения — разные настройки.

Хранить для каждой локали: код, дату проверки, источник, владельца перевода, готовность интерфейса и графики. Если сторонний инструмент использует allowlist, новая локаль из обновленного списка требует проверки источника и обновления списка. Локальный validator этого набора проверяет синтаксис тега; поддержка магазином проверяется отдельно.

Собственные переводы и localized graphics выбираются по языку пользователя; если локализованных visuals нет, могут показываться материалы default language. Автоматический перевод листинга не означает локализованный Android UI или проверенную маркетинговую речь. Для изменений оффера по стране/аудитории существует отдельный механизм [custom store listings](https://support.google.com/googleplay/android-developer/answer/9867158?hl=en), включая Search keywords targeting. Это выбор аудитории карточки, не скрытый keyword field основной `Listing` schema и не ручная рекламная ставка. Bundled Publisher CLI custom listings не управляет.

Рабочая locale matrix:

```text
country / listing / locale → audience intent → локальные источники фраз
→ title / shortDescription / fullDescription readiness
→ Android UI / graphics / paywall readiness → QA owner / checked_at / gaps
```

Приоритет перевода выбирать по product availability, данным существующих пользователей/сценариев и ресурсам поддержки. Не заполнять новые локали английскими keyword lists ради воображаемого cross-localization бюджета. Не предполагается, что одна страна соответствует одному языку или отдельному default listing.

## Правдивость и оформление

Название, иконка и developer name не должны содержать emoji, повторяющиеся спецсимволы, заявления о рейтинге, цене, акциях или принадлежности к программам Play. ALL CAPS допустим как часть бренда. Описание не превращать в список ключевых слов или анонимные отзывы. Источник: [Metadata policy](https://support.google.com/googleplay/android-developer/answer/9898842?hl=en-GB).

## Рабочий процесс этого набора

1. Сначала записать фактические возможности: что бесплатно, что платно, нужен ли аккаунт, интернет, разрешения, подписка.
2. Выбрать один основной пользовательский сценарий и естественные формулировки из исследования. Они должны объяснять продукт.
3. Составить несколько вариантов title/short description. Не обещать рост ранга из-за конкретного числа повторений.
4. В full description раскрыть сценарии, функции и ограничения. Максимальная длина — предел, а не цель.
5. Для каждой локали проверить длину после перевода; проверить читаемость носителем языка и согласованность текста со скриншотами и сборкой.
6. Сохранить готовый текст отдельно от исследовательского keyword bank. В листинг передавать только реальные поля.

## Как писать каждое поле

Ниже редакционная методика, не ranking formula или дополнительное требование Google.

**Title:** узнаваемое название и ясный основной сценарий, если оба естественно помещаются. Сравнивать варианты по узнаваемости бренда, точности и читаемости на устройстве; не добавлять все secondary intents. Рабочий паттерн `[Brand]: [основная задача]` полезен лишь если соответствует бренду и лимиту. Не удалять нужные языковые частицы ради English token budget.

**Short description:** одно понятное обещание поддерживаемого результата и, если полезно, конкретное отличие. Это самостоятельный текст: пользователь может увидеть его без полного описания. Не повторять title дословно, если повтор ничего не объясняет; общий термин в естественной фразе сам по себе не запрещен. Варианты лучше отличать оффером, а не случайной перестановкой ключей.

**Full description:** сначала основная задача и кому полезен продукт; затем несколько конкретных сценариев/функций и существенные условия. Удобная редакционная структура:

1. Понятный результат и контекст применения без необоснованных превосходных степеней.
2. Сценарии в формате действие → польза, подтвержденные текущей сборкой.
3. Значимые ограничения: платные возможности, аккаунт, интернет/совместимость, permission-dependent опыт — в применимой части.
4. Помощь/поддержка и ссылки, если они нужны продукту и policy. Ссылки privacy/deletion, declarations и billing должны быть на нужных поверхностях; текст description не заменяет их.

Нет обязательной длины вступления «167 символов», keyword density, минимума уникальных слов или заполнения 4000 символов. Для поисковых фраз использовать понятные context/synonyms без word blocks. Проверять реально видимый первый экран текста, особенно после локализации. Выгода не является evidence эффективности; заявления требуют подтверждения и применимого policy review.

## Локализация и QA

Переводить смысл оффера, сохраняя продуктовые факты и отдельно проверяя язык запросов. Для каждого языка проверить:

- Термины аудитории и естественную грамматику; если human/native QA недоступен, честно пометить этот этап.
- Согласованные brand/function названия в listing, UI, screenshots, paywall и support.
- Реальные условия монетизации, единицы/форматы и доступность обещанного сценария в рынке.
- Длину окончательного Unicode текста и фактическое отображение доступным способом; RTL, переносы и CJK layout требуют осмотра.
- Точные locale codes и совпадение языка listing с подготовленной графикой. Текстовые assets не локализуют UI автоматически.

Сохранить source text, окончательные варианты и rationale. Машинный перевод может быть черновиком, но не обозначается как подтвержденный human QA. Для отсутствующей функции исправлять обещание, а не искать более удобный перевод.

## Формат передачи и проверка

Рабочий JSON набора — map locale → API fields:

```json
{
  "en-US": {
    "title": "Focus Timer",
    "shortDescription": "Plan focus sessions and follow your progress.",
    "fullDescription": "Start a focus session, take a break, and track your progress."
  }
}
```

Это иллюстрация структуры, не исследованный оффер для приложения пользователя. `title`, `shortDescription`, `fullDescription` обязательны для каждой переданной locale. Дополнительный `video` — YouTube URL; в bundled live update отсутствие video сохраняет текущую ссылку, `"video": ""` означает запрос удаления. Не передавать keyword bank, ranking или review findings как дополнительные Listing fields.

Локальная проверка выявляет schema/length issues и редакционные warnings. Перед передачей дать краткую таблицу locale/field, длина, rationale и QA gaps. Если существует baseline, показать before/after; без него не заявлять сравнение с живым магазином. Последовательность API и backup — в [Publisher guide](../docs/play-api.md).

Изменения проходят разные состояния: draft, local checked, remote validate, commit, review/publishing, фактическая видимость. Для следующего измерения сохранить время появления карточки и проверенный контекст рынка/языка. Commit не гарантирует мгновенного появления или фиксированного срока индексации.

Локальный счетчик помогает найти превышение, но финальное принятие текста проверяет Play Console. HTML, emoji и сложные Unicode последовательности требуют проверки отображения; не обещать идентичный подсчет каждым сторонним инструментом.
