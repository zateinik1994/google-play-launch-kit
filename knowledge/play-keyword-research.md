# Исследование поисковых формулировок Google Play

Проверено: **2026-10-14**. Keyword bank здесь — исследовательский документ, а не скрытое поле загрузки. Ниже методология набора: она не утверждает веса Google и не подразумевает встроенный сбор данных.

## Что можно считать данными

В изученных публичных Play Console/Developer API документах нет универсального публичного показателя Search Popularity для каждого запроса, аналогичного привычным workflow Apple Search Ads. Не придумывать для Play точную частотность, difficulty, число конкурентов или установки по запросу. Если они пришли от ASO-провайдера, сохранить его название, определение показателя, рынок, дату и метод доступа; это оценка провайдера.

| Источник | Что дает | Ограничение |
| --- | --- | --- |
| Собственный Play Console: search term, exports | Фактические данные собственного листинга в доступном отчете | Не общий объем рынка; структура и доступность отчета меняются |
| Наблюдение выдачи Play и подсказок | Язык запросов, варианты задач, видимые конкуренты | Зависит от устройства, аккаунта, языка, страны и времени |
| Отзывы, интервью, support | Слова пользователей и реальные проблемы | Это качественная обратная связь, а не частотность |
| Google Trends | Относительный интерес в Google Search | Это не объем поиска Play; шкала нормализована |
| Google Ads Keyword Planner | Идеи и оценки для Google Search | Это не каталог Play и не его органическая конкуренция |
| ASO-сервис | Его оценка спроса/сложности | Воспроизводимость зависит от его методологии |

Про текущие search term dimensions: [Play Console performance](https://support.google.com/googleplay/android-developer/answer/9859173?hl=en). Про поисковые данные Google: [Trends FAQ](https://support.google.com/trends/answer/4365533?hl=en-GB). Список методов API: [Google Play Developer API](https://developers.google.com/android-publisher/api-ref/rest).

## Бриф и scope рынка

Записать основной job пользователя, аудиторию, контекст использования, реальные функции Android-сборки, монетизацию и ограничения. Формулировка «для людей, которым нужен результат X в условиях Y» помогает отличить запрос о нашей функции от просто популярной темы. Пользовательские факты важнее списка слов конкурента.

Развести три измерения: страна распространения, язык пользователя и locale listing. Например, жители одной страны могут видеть разные переводы и иметь разные задачи. Матрица рынка содержит country → язык/locale → доступность → готовность UI/графики → evidence. Приоритет нового рынка зависит от product fit, доступности поддержки/покупок и данных команды; универсальный список «сначала пять самых больших языков» здесь не применяется.

Когда доступа к Console нет, продолжить по открытым карточкам, речи аудитории и доступным экспортам. Результат остается desk research. Если нет package, не заполнять вымышленным ID реальную таблицу; выбранный package понадобится для наблюдений своего приложения и live-операций.

## Конкурентная выборка

Включать приложения по задаче пользователя, а не только по категории магазина:

| Группа | Зачем смотреть | Что не переносить автоматически |
| --- | --- | --- |
| Прямые конкуренты | Те же основные задачи, аудитория и доступность | Их функцию или монетизацию в наше обещание |
| Смежные альтернативы | Иной способ решить ту же проблему | Их жанр/спрос как наш рынок |
| Референсы подачи | Ясность оффера, порядок доказательств, локальный язык | Утверждение об эффективности чужой графики без эксперимента |

Если пользователь назвал конкурентов, проверить список и дополнить лишь обнаруженным существенным пробелом. Для discovery использовать seeds и доступный Play контекст. Web search находит страницы, но не воспроизводит поиск Play. Не задавать обязательный размер выборки: объяснить какие сценарии/сегменты она покрывает и какие пропускает.

Карточка конкурента: package/URL, observed_at, country/locale/method, причина включения, видимые title/descriptions, основной оффер, подтвержденные или только заявленные функции, монетизация, первые screenshots, видимые рейтинги/число оценок с контекстом. Сохранять raw evidence. Если поле не получено, писать `unavailable`, а не достраивать из другой локали.

Не выводить месячные installs из public download badge, выручку из числа отзывов, advertising spend из роста рейтинга. Измерение provider имеет собственную единицу/период и пометку estimate; источник не становится фактом только потому, что вернул JSON.

## Карточка запроса и CLI-контракт

Для каждого запроса хранить:

```text
query: оригинальная формулировка
locale / country / device: контекст наблюдения
intent: какую задачу пользователь хочет решить
product_fit: есть ли этот сценарий в текущей сборке
source: URL либо точный путь к экспорту
observed_at: YYYY-MM-DD
metric_name / value / unit: только если источник их действительно содержит
confidence: observed / provider-estimate / hypothesis
candidate_field: title / shortDescription / fullDescription / research-only
```

Неизвестное значение в человеческом отчете записывать `unknown`, а не `0`: ноль означает измеренное отсутствие. Для bundled CSV numeric `volume` оставлять **пустым**; строка `unknown` не является числом и не пройдет CLI. Полная исследовательская карточка хранится отдельно: произвольные дополнительные поля не обязательно попадают в JSON результата инструмента.

Минимальный CSV: `query,locale,country,source,relevance`; дополнительные поддерживаемые поля: `volume,volume_source,note`. Если volume заполнен, `volume_source` обязателен; определение/units/period записать в note. Другие показатели провайдера, например opportunity или difficulty score, не переименовывать в volume.

`relevance`: 0 — неподдерживаемая функция или нерелевантный запрос; 1 — смежный сценарий; 2 — полезная подтвержденная функция; 3 — основная задача. CLI сохраняет 0 как `decision: excluded`, сортирует по relevance/алфавиту, не вычисляет demand или competition. Одна и та же query/locale/country с разными source допустима как разные наблюдения; повтор внутри одного source отклоняется. Из этих наблюдений редактор составляет shortlist, сохраняя происхождение evidence.

## Порядок исследования

1. Зафиксировать brief и locale matrix; определить, какое решение требуется сейчас — оффер, новая локаль, текст или диагностика падающего трафика.
2. Получить seeds из product truth и пользовательской речи; собрать выбранных конкурентов и доступные тексты/отзывы с источниками.
3. Расширить universe через объект/действие, проблему/результат, подтвержденный контекст. Например, для реального habit checklist связаны «habit tracker» и «daily habit checklist»; «medical diagnosis» не становится кандидатом только из-за близкой wellness темы. Примеры не являются измеренными запросами.
4. Сгруппировать по намерению, нормализовать пробелы/регистр для анализа, сохраняя исходное написание. Не удалять значимые частицы и формы только по English stop-word списку; японские, арабские и другие тексты требуют языкового анализа. Подсказки и отсутствие подсказки не определяют точную частотность.
5. Проверить product fit каждого кластера и классифицировать competitor/listing gaps ниже. Чужие бренды выделить для исследования, не переносить в видимые тексты автоматически.
6. Составить рабочий shortlist с причинами, field mapping и unknowns. Если нужны собственные позиции, снять контекстные наблюдения с одинаковой глубиной/методом, иначе не обещать измерение конкурентности.
7. Подготовить по локали естественные варианты title/short description и полный текст выбранного оффера, затем проверить [metadata](play-metadata.md).
8. Сохранить решение и baseline/следующую проверку по [metrics](play-metrics.md). Передача research в copy или ads assets не доказывает performance.

## Gap-анализ без выдуманного opportunity score

Построить матрицу `intent cluster → product evidence → пользовательская речь → оффер конкурентов → наше текущее покрытие → действие`. Число конкурентных упоминаний — count внутри выбранной выборки, не число всех конкурентов рынка. Различать:

| Наблюдение | Допустимый вывод | Следующее действие |
| --- | --- | --- |
| Наша подтвержденная функция не объяснена | Есть пробел в нашей коммуникации | Сформулировать понятный оффер и проверить |
| Аудитория использует иной термин | Есть кандидат локального языка | Сохранить evidence и проверить естественность |
| Все выбранные direct competitors обещают то же | Требуется ясное доказательство отличия | Найти подтвержденный differentiator |
| Конкуренты не употребляют фразу в title | Фраза не видна в выбранных titles | Проверить намерение/выдачу, не объявлять нишу свободной |
| Запрос требует отсутствующей функции | Несоответствие продукту | Exclude для карточки; optional product backlog |
| Оценки спроса/ранга отсутствуют | Возможность пока не измерена | Дать качественную гипотезу и путь проверки |

Приоритет выбирать по product fit, надежности evidence, ясности для аудитории и возможности проверить эффект. Если demand известен, сравнивать только совместимые показатели одного определения/источника/периода/рынка. Нет основания назначать «конкуренция LOW» по порогу рейтингов топ-3 или срок выхода в топ по длине запроса.

## Локальное ядро и передача в карточку

Для каждой locale заново проверить пользовательские фразы и direct competitors; перевод shortlist сам по себе не подтверждает спрос. Более конкретный long-tail полезен, когда точно описывает поддерживаемую задачу, а не потому, что любой запрос из четырех слов легко ранжируется. Head/long-tail без demand использовать только как описательные категории, не как числовые tiers.

В title показать узнаваемое название/основной сценарий; short description раскрывает ценность; full description объясняет функции и условия. Не собирать word blocks. Нет обязательного числа уникальных слов, заполнения 85% лимита или нового keyword budget от дополнительных локалей. Покрытие оценивается по подтвержденным intent clusters и читаемости. Важное повторение в естественной фразе допускается; repetitive spam остается риском.

Результат исследования: scope/locale matrix, конкурентная таблица с sources, universe + исключения, gap matrix, shortlist + rationale, drafts/Listing JSON и missing evidence. Хранить список исключенных решений помогает не возвращать нерелевантные обещания в следующей сессии.

Google прямо связывает обнаружение с понятным, полным листингом и рекомендует избегать перегрузки текста ключами: [Get discovered on Google Play search](https://support.google.com/googleplay/android-developer/answer/4448378?hl=en).

Не переносить Apple Search Ads CPC, SP или keyword rank в Google Play таблицу под теми же названиями. При сравнении платформ оставлять отдельные колонки с явной платформой и источником. App campaign conversions не раскрывают автоматически organic keyword demand; этот набор не реализует keyword scraping, сторонние ASO API или автоматический competitor gap calculation.
