# Мониторинг ASO Google Play

Прочитай [метрики](references/knowledge/play-metrics.md), включая изменения Store listing performance 2026 года. Начни с периода, приложения, рынков, локалей и изменений карточки/релизов/рекламы за этот период. Регулярное расписание создавай только по поручению пользователя и средствами доступного агента.

## Сопоставимые наблюдения

CSV-снимки позиций должны иметь колонки `observed_at,package_name,locale,country,query,rank,depth,source`. Timestamp — ISO-8601 с часовым поясом. `rank` — место начиная с 1; пустое значение означает «не найдено в первых depth», а не ноль. В `source` включи провайдера/профиль измерения и контекст устройства. Один запрос в одном контексте — одна строка в снимке.

```bash
python3 <путь-скилла>/references/shared/cli.py ranks reports/before.csv reports/after.csv --output reports/rank-changes.json
```

Команда сравнивает предоставленные данные. Она не получает позиции из Google Play. Положительное `positions_gained` означает подъем. Изменение source/depth, отсутствие строки и выход за глубину не дают точного числового изменения.

## Отчет

Сопоставь результаты со сменой метаданных, сезонностью, релизами, доступностью по странам и рекламой. Не утверждай причинность по одному before/after. Для показателей Console зафиксируй название метрики, знаменатель и версию отчета. Современный click CTR и legacy acquisition conversion нельзя соединять в один временной ряд.

Предложи следующую проверяемую гипотезу: изменение, ожидаемый эффект, основная метрика, ограничения выборки, контроль качества пользователей и срок/условия оценки. Store listing experiment и наблюдение ранга решают разные вопросы. Читай [план эксперимента](references/docs/experiment-template.md), когда нужен A/B тест.

Итог: сопоставимый отчет, данные без наблюдений, объяснения с уровнем уверенности и приоритет следующей итерации. Выручку и paid conversions оценивай по согласованной атрибуции, не вычитанием двух несопоставимых источников.
