# ASO-исследование Google Play

Собери проверяемый ASO-набор: контекст продукта → конкуренты → фразы и намерения → пробелы позиционирования → локализованный текст → baseline следующей итерации. Для узкого поручения выполняй только нужную часть; исследование органики не дает разрешения на рекламу или изменение Console.

## 1. Контекст и рабочие материалы

Найди в материалах или уточни лишь отсутствующие факты: package name/ссылку, основной сценарий и аудиторию, реальные Android-функции, бесплатные и платные возможности, ограничения, страны распространения и языки. Если переносится iOS-приложение, проверь отличия Android onboarding/paywall и доступных функций. Для нового приложения package name может быть еще не выбран: исследование этим не блокируется.

Прочитай [принципы](references/knowledge/play-foundations.md) и [методику исследования](references/knowledge/play-keyword-research.md). Для текста используй [поля и локализацию](references/knowledge/play-metadata.md). Сохраняй исходные наблюдения отдельно от выводов в выбранной папке пользователя, например `research/raw/`, `research/`, `metadata/`, `reports/`. Учебные данные в `references/examples/` не являются исследованием приложения.

Для каждого целевого рынка составь строку: country, listing locale, язык аудитории, доступность приложения, готовность Android UI/графики, источник проверки. Страна и локаль не взаимозаменяемы; готовый English keyword bank не заменяет исследование на другом языке.

## 2. Конкуренты и их предложения

Если список уже дан, проверь приложения и их релевантность. Если списка нет, начни с нескольких формулировок основной задачи и доступных наблюдений Play. Для bounded public collection или AppStoreSpy прочитай [сбор данных](references/docs/aso-data-api.md). Браузер/эмулятор и предоставленные экспорты также подходят; порядок web search не является Play search rank.

```bash
python3 <путь-скилла>/references/shared/store_data.py search --query 'habit tracker' --locale en-GB --country GB --limit 20 --output research/search.json
python3 <путь-скилла>/references/shared/store_data.py profiles --package com.example.myapp --locale en-GB --country GB --output research/profiles.json
```

Подставь реальные запросы/package. Эти команды делают публичное сетевое чтение и требуют optional `google-play-scraper`; источник, версия parser и контекст сохраняются. AppStoreSpy по умолчанию строит offline-plan; `--execute` расходует credits и может инициировать сбор у провайдера. Используй его в разрешенном scope и сохраняй provenance модельных оценок.

Раздели прямых конкурентов с тем же сценарием, смежные альтернативы и сильные референсы оформления. Выбирай размер выборки по охвату сценариев; большая нерелевантная выборка не улучшает анализ. Сохрани причины включения и исключения.

Для каждого релевантного приложения запиши package/URL, рынок/язык/дату, title, доступные descriptions, основной оффер, фактические функции, монетизацию и первые визуальные аргументы. Различай заявления карточки и проверенное поведение. Рейтинг, число оценок и публичный download badge не доказывают текущие monthly installs или выручку; оценки сервиса храни с именем модели/провайдера.

Сравни предложения в таблице по пользовательской задаче. Если доступны отзывы, используй их для языка аудитории и повторяющихся барьеров, отмечая период/язык/выборку. Не добавляй конкурентную функцию в наше обещание без product evidence.

## 3. Keyword universe и приоритеты

Получи seeds из подтвержденных задач, речи пользователей, релевантных конкурентных текстов, доступных подсказок/выдачи и Console/ASO-экспортов. Расширяй намерение: объект + действие, проблема, результат, значимый контекст. Сохраняй оригинальные фразы, локальные варианты и источник; не генерируй перестановки только ради числа слов.

Для кандидатов из собранных профилей доступен [offline discovery](references/docs/aso-tools.md):

```bash
python3 <путь-скилла>/references/shared/aso_tools.py discover --profiles research/profiles.json --seed 'habit tracker' --output research/candidates.json
```

Он считает число документов с фразой внутри отдельных полей, сохраняет значимые числа и metadata/locale/country сборщика, оставляет volume неизвестным и требует product-fit разметки. Raw список без metadata нужно самостоятельно привязать к рынку/языку. Для пользовательской речи можно взять `recurring_phrases` из [review analysis](references/docs/aso-tools.md), прочитав review IDs и проверив продуктовую релевантность. Для Google Search Keyword Planner доступен отдельный [Ads keyword-ideas](references/docs/google-ads-api.md); его объем Google Search не является объемом Google Play.

Сгруппируй по намерению и размечай relevance 0–3: 0 — неподдерживаемое/нерелевантное; 1 — смежный сценарий; 2 — полезная функция; 3 — основной сценарий. Это редакционная оценка. Отдели чужие бренды и информационные запросы, не подходящие для обещания карточки.

Для CSV используй `query,locale,country,source,relevance,volume,volume_source,note`. Неизвестный volume оставляй пустым; если источник дает показатель, запиши его определение, единицы, период и дату в `note`. Официального универсального Play Search Popularity 0–100 этот набор не предоставляет.

```bash
python3 <путь-скилла>/references/shared/cli.py keywords research/keywords.csv --output research/keyword-bank.json
```

`<путь-скилла>` — абсолютный путь к этому скиллу. CLI сортирует по указанной relevance, затем алфавиту; это нормализация, не итоговый opportunity score. Он не собирает Play данные и не сравнивает объем разных провайдеров как одну шкалу. Relevance=0 остается в банке с `decision: excluded` для аудита, но не входит в shortlist.

## 4. Gap-анализ и рабочий shortlist

Для важных intent clusters сопоставь: подтвержденную нашу функцию, слова аудитории, предложения выбранных конкурентов, текущий наш текст/графику и доступные измерения. Классифицируй пробел: наша функция плохо объяснена; аудитория использует иную фразу; конкуренты уже обещают то же; продукт не поддерживает запрос. Отсутствие фразы в title конкурентов означает пробел текста выбранной выборки, а не доказанную свободную нишу.

Если нужны позиции, запиши query, страну, язык, время с timezone, устройство/метод и глубину; отдели рекламу от выбранного метода учета органических результатов. Без наблюдений не рассчитывай difficulty или ожидаемый rank. Приоритет shortlist определяй product fit → качество evidence → ясность оффера → доступная проверка, а не выдуманной частотностью.

После разметки банка `python3 <путь-скилла>/references/shared/aso_tools.py gaps --keywords research/keyword-bank.json --listings metadata/listings.json --profiles research/profiles.json --output research/text-gaps.json` проверяет точные token phrases в собственных и конкурентных полях. `--profiles` опционален и требует metadata locale/country; несовместимые контексты и отсутствующие конкурентные поля остаются неизвестными. Проверь `observations` и разреши `decision_conflict` по product evidence. `text_gap` не означает свободную поисковую нишу или отсутствие индексации.

Для каждого кандидата укажи кластер, evidence, вариант использования (`title`, `shortDescription`, `fullDescription`, визуальный оффер или research-only), причину выбора/исключения и неизвестные данные. Не нужен универсальный минимум слов или заполнение всех лимитов. Если важный сценарий остался без локального evidence, расширь именно этот пробел либо обозначь гипотезу.

## 5. Тексты, локали и передача результата

Для каждой целевой локали подготовь варианты title/shortDescription с разными проверяемыми офферами, объясни tradeoff узнаваемости и ясности. Затем напиши fullDescription выбранного варианта: основной результат → сценарии/функции → существенные условия. Не переноси iOS subtitle, keyword field, cross-localization budget или запрет любого повтора между полями. Учитывай локальную речь, поддерживаемые locales, текст Android UI и реальные условия монетизации.

Сохрани JSON вида `{"en-US":{"title":"…","shortDescription":"…","fullDescription":"…"}}` отдельно от keyword bank, проверь:

```bash
python3 <путь-скилла>/references/shared/cli.py validate metadata/listings.json
```

Validator проверяет форму и пределы, а не смысл, перевод, поддержку locale или policy approval. Проверь отдельно product truth, читаемость, согласованность со скриншотами и отображение доступным способом.

Для передачи нескольких локалей заполни [offline locale inventory](references/docs/readiness.md): `python3 <путь-скилла>/references/shared/readiness.py report --project project.json --listings metadata/listings.json --output reports/locale-readiness.json`. Он сопоставляет выбранные locales с текстами и optional assets/evidence; `INCOMPLETE` показывает пробелы, `CHECKLIST_RECORDED` лишь фиксирует предоставленные evidence records и не означает approval Google.

Передай только артефакты нужного scope:

- Product brief и locale matrix с неподтвержденными фактами.
- Конкурентную таблицу, источники/дату/контекст и gap-анализ.
- Keyword bank со всеми decisions и отдельный приоритетный shortlist.
- Варианты текста, рекомендуемый вариант с обоснованием и валидированный Listing JSON.
- План baseline/следующей проверки: primary metric, источник, сегмент, confounders и guardrails по [метрикам](references/knowledge/play-metrics.md).

Для нового приложения baseline может отсутствовать: запиши, что снять после выпуска, без имитации «до». Заверши конкретными ограничениями исследования и следующим шагом. API commit, создание эксперимента и графики выполняются только когда входят в поручение; подготовленный ASO-набор сам их не запускает.
