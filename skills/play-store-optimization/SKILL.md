# Оптимизация карточки Google Play

Выбери режим: аудит готовых metadata, анализ выборки отзывов, диагностика карточки или план Store listing experiment. Для одной проверки JSON не запускай полный ASO-процесс. Входы: приложение/locale/listing, фактические функции и монетизация, текущий материал, доступные источники и цель поручения. Отсутствие live Console допускает локальный результат с указанными пробелами.

## Метаданные и редакционный аудит

Прочитай [поля и workflow](references/knowledge/play-metadata.md). Проверяй файл выбранных локалей:

```bash
python3 <путь-скилла>/references/shared/cli.py validate metadata/listings.json
```

`<путь-скилла>` — абсолютный путь к этому скиллу. Сначала устрани ошибки структуры/длины, затем проверь product truth и условия платных функций, ясность основного оффера, релевантность текста, естественную речь, поддержку locale и согласованность с фактическими Android UI/графикой. Не расширяй простой JSON-аудит до build/policy audit без причины; confirmed issue укажи отдельно от unverified.

`audit.warnings` — редакционные эвристики. Счетчик использует Unicode code points; поддержка locale, отображение и policy окончательно проверяются отдельно. Нет официального «ASO-скора» этого набора: полнота карточки и длина текста не прогнозируют позиции.

Дай таблицу field/locale → проблема и evidence → исправление → способ проверки. Для предложенных правок покажи before/after и rationale. Если готовится загрузка, optional offline diff доступен через `references/shared/play_api.py plan --input listings.json --current before.json` по [API guide](references/docs/play-api.md); без baseline он не знает текущих значений магазина. Аудит не делает commit.

## Отзывы

Сначала установи происхождение и объем выгрузки, период, языки, версии и доступные фильтры. Bundled tool не загружает отзывы из Play. Сохрани raw файл; подготовь CSV `review_id,rating,text`, отдельно отделив нужные version/country/period. Дополнительные поля можно хранить в исходнике, но CLI не фильтрует по ним. При отсутствии этих полей ограничения выборки остаются неизвестными.

Убери дубли по ID по явному правилу, сохрани связь с raw данными. Обновленный отзыв не считается новым уникальным пользователем; конфликтующие версии одного ID требуют выбора записи по имеющейся дате. CLI отклоняет повтор ID, он не решает эту задачу автоматически.

Если экспорт не содержит review ID, проверь доступные устойчивые идентификаторы/ссылки источника. Локальный record ID можно использовать для трассировки, но он не доказывает уникальность отзывов или пользователей. При невозможности dedup назвать ограничение и не представлять count как полный уникальный охват.

```bash
python3 <путь-скилла>/references/shared/cli.py reviews research/reviews.csv --output reports/reviews.json
```

Средняя оценка в CSV — среднее выбранных записей, не публичный Play rating. Словарь тем работает для EN/RU и не является sentiment model: метки пересекаются и ошибаются, их сумма может превышать число отзывов. Для других языков подготовь ручной/доступный агенту анализ с явным методом, сохраняя оригиналы. Прочитай низкие оценки и примеры положительных сценариев; проверь контекст, отрицания и известные дефекты.

Раздели product bugs, billing/trust, UX, mismatch обещания карточки и новые feature requests. Для каждой важной темы дай count/denominator, подтверждающие review IDs и короткие выдержки, severity, текущую feature evidence и рекомендуемый адресат изменения. Просьба о несуществующей функции не превращается в keyword карточки. Частота темы в удобной выборке не является распространенностью среди всех пользователей.

Если нужны ответы, подготовь конкретные drafts без ложного обещания исправления или раскрытия личных данных. Публикуй только когда это входит в поручение. Выход: dataset scope, distribution, вручную проверенные темы, ограничения метода и приоритетный product/listing backlog.

## Диагностика карточки

Используй [воронку и decision gates](references/knowledge/play-metrics.md) для предоставленных метрик. Назови bottleneck: недостаток релевантного discovery, слабый click intent, разрыв до первого запуска, activation/retention или плохое качество. Нельзя выводить причину из одного падения rate без знаменателя, сегмента и timeline изменений.

Для проверки конкурентного оффера следуй [research](references/knowledge/play-keyword-research.md); для графики — [creatives](references/knowledge/play-creatives.md). Сохраняй приоритеты как evidence/impact/effort/verification, а не придумывай универсальный health score или benchmark. Техническая ошибка и misleading claim исправляются в разрешенном scope без ожидания A/B; вкусовую гипотезу можно проверить экспериментом.

## Эксперимент

Прочитай [экспериментальный цикл](references/knowledge/play-metrics.md) и заполни [шаблон](references/docs/experiment-template.md). Проверь eligibility listing и доступный experiment type в текущей Console; toolkit не создает и не применяет эксперименты через API.

1. Запиши барьер и evidence, целевую аудиторию и одну гипотезу. Выбери действительно поддерживаемый asset; title не обещай как штатную экспериментальную поверхность.
2. Сохрани current control и variants. Изменяй один существенный элемент, если цель — узнать его эффект. Больше изменений допустимы как тест общей концепции, но не дают эффекта каждого элемента по отдельности.
3. Запиши точную target metric, доступные audience/MDE/confidence settings, ожидаемую пригодность трафика, product guardrails и правило остановки. Не обещай универсальную sample size или победу за фиксированный срок.
4. После фактического запуска проверь язык, material delivery и отсутствие concurrent изменений, способных исказить вывод. Не трактуй подготовленный draft как работающий experiment.
5. Оцени результат по current Console status/interval и практической полезности. `More data needed` или draw не становятся победой. При вреде пользователям останавливай по заранее заданному условию; ранний удачный процент сам по себе не повод применять вариант.
6. Сохрани результат, ограничение причинности, решение и дату следующей проверки. Применение варианта должно соответствовать существующему поручению пользователя.

Финал содержит план/фактический статус, исходные материалы, выбранную метрику, невыполненные gates и конкретное следующее действие. Новый CTR и legacy acquisition CVR относятся к разным результатам; улучшение клика не доказывает activation, retention или выручку.
